# データベース契約

本サーバーは `jvdata-bridge` が構築する PostgreSQL データベースを読み取り（Read-only）、MCP 構造化データとして返却します。データベースの更新・書き込みはサポートしません。

---

## 🔄 データの処理フロー

1. **ツール選択**: MCP クライアント（AI エージェント）が固定ツールまたは SQL メタデータツールを選択。
2. **クエリ構築**: 固定ツールは事前定義されたSQLを使用。カスタム分析ではAIエージェントがスキーマを確認してSQLを構築。
3. **AST 安全性検証**: カスタムSQLを `sqlglot` でPostgreSQLのASTへ解析し、安全性を検証。固定ツールは各実装のSQLを使用。
4. **クエリ実行**: 読み取り専用トランザクションおよびタイムアウト制限下で実行。
5. **出力シリアライズ**: 固定ツールは Pydantic モデルへ変換。カスタム SQL はカラム名付きの行リストへ変換。

カスタムSQLの本文はMCPクライアントが構築し、ゲートウェイが検証・正規化と外側の取得件数制限を適用します。

## 🗄️ 標準 read model スキーマ

対象スキーマは以下の 3 つに固定されています（環境変数での変更不可）。

| スキーマ | 概要 |
| --- | --- |
| `jv_data` | 基礎競馬データ |
| `jv_mart` | 競馬分析用 read model |
| `jv_ref` | マスタ・参照データ |

### 予測用の速度read model

同梱線形モデルの勝率・複合分析と速度付き特徴量には、対象レースの出馬表に加えて、全出走候補馬の
`jv_mart.horse_speed_quality` が必要です。このデータはDB側で事前に準備し、MCPサーバーは
読み取りだけを行います。ペース・位置の計算は、速度表示の欠測だけでは停止しません。
採用済みJSONの能力特徴量は学習時の欠測処理に従います。モデルの契約は[モデル開発](model-development.md)を参照してください。

速度値は `race_id`、`race_date`、`horse_id`、`model_version` で照合します。
モデル版は `temporal-linear-v3-speed-2026-holdout`。履歴排他日は対象レース日です。
レースコード先頭8桁は開催日を表し、発走時分は含みません。成績・調教・騎手実績は
対象日前の記録に限定します。公開出力の `history_before_date` は対象レース日から決まる
履歴の排他的な日付上限であり、DBで実測した取得時刻ではありません。
日付上限は対象レースから計算し、速度read modelに取得時刻の列を要求しません。
対象馬の速度行が欠ける、または値が契約範囲外なら、欠損件数を示すエラーを返します。
対象日以降の履歴を含む速度行や、欠損を埋める中立値には切り替えません。

DBの `speed_quality_raw` は最大5走の減衰加重平均です。読取時に `speed_observation_count` から
重み合計を求め、`(平均 × 重み合計 + 1) / (重み合計 + 2)` で平滑化します。
`speed_quality_coverage` と `speed_baseline_level` は保存値を使い、レース内の順位へ変換します。
DB側で速度値の定義を変更する場合は、二重補正を防ぐためモデル版と読取側も同時に更新してください。

`doctor` は接続と `races`、`race_cards`、`latest_win_place_odds` の存在を確認します。
`ok: true` でも、速度read modelの全馬被覆や各ツールに必要なデータの充足まで確認したことにはなりません。

## 🛡️ カスタム SQL の実行制約 (`sql_execute_custom_query`)

安全性を担保するため、以下の制約をすべて満たす SQL のみ実行を許可します。

### 1. 構文とセキュリティ

* 単一の PostgreSQL `SELECT` / `WITH` 文であること（複数文・SQL コメント不可）。
* テーブル参照はゲートウェイの許可参照面に限定し、許可スキーマ（`jv_data`, `jv_mart`, `jv_ref`）による**明示的なスキーマ修飾が必須**（未修飾・カタログ参照・許可外スキーマは拒否）。
* 書き込み操作（`INSERT`, `UPDATE`, `DELETE`, `CREATE`, `DROP`, `TRUNCATE`, `SELECT INTO` 等）の禁止。
* 副作用のある関数、ユーザー定義関数、行ロック（`FOR UPDATE` 等）の禁止。
* パラメータバインド: 名前付きプレースホルダー（`:parameter`）を使用し、`parameters_json` 経由で指定（文字列連結は禁止）。

### 2. 行数制限 (LIMIT)

外側の返却上限は `max(1, min(max_rows, JVDATA_BRIDGE_MCP_MAX_ROWS, 1000))` です。
SQL本文の `LIMIT` が小さい場合、実際の返却数はさらに少なくなります。

* **標準設定**: 引数既定値 `100` / 環境変数既定値 `200` / **絶対上限 `1000`**

応答には `effective_limit`, `returned_count`, `truncated`, `next_cursor` を含めます。
有効上限より1行多く読み、続きがあるかを確認します。`ORDER BY` がある同じSQL・パラメータ・設定では、
返された `next_cursor` を `cursor` に渡して続きの取得ができます。順序は一意になる列を含めてください。
ページ間でDBが更新された場合の同一スナップショットは保証しません。
`ORDER BY` がない場合は継続カーソルを返さず、必要な順序指定を応答で説明します。

### 3. 高コストテーブルと事後データ制限

* **`jv_mart.latest_odds` / `jv_mart.odds_history`**: そのテーブルを直接制限する `race_id` の等価条件、または上下限を指定した `race_date` の範囲条件が必須。別名を解決し、各SELECTスコープと各OR分岐を検証します。別のテーブルや内側の副問い合わせの制限では代用できません。
* **`pre_race_mode=true`**: 確定結果や事後オッズなどの事後データ参照を自動遮断。
* **`context="pre_race_prediction"`**: `pre_race_mode=true` と同じ参照制約を適用。他のcontextを指定しても、trueの制約を解除しません。
* **日時範囲**: 対象レースや現在時刻による条件はSQLに明示します。発走前の参照制約だけでは、履歴の日時範囲は限定されません。

## ⚙️ 固定ツールの値正規化仕様

データ解釈の揺れを防ぐため、固定ツールでは以下の規約に基づき値を正規化します。

### 1. 券種（オッズ）

* **正規化コード**: `win`, `place`, `quinella`, `exacta`, `wide`, `trio`, `trifecta`, `bracket_quinella`
* `odds_table.bet_type` はこの8コードを指定します。未知の券種や日本語の別名は受け付けません。

### 2. 日時の意味とオッズタイムスタンプ

利用する日時と意味は次のとおりです。実際のDB取得時刻と取り込み遅延は不明として扱い、推測しません。

| 項目 | 利用目的と制約 |
| --- | --- |
| `scheduled_start_at` | 発走予定日時。当日の前後関係の確認に使い、実際の発走・結果公開時刻とは扱わない |
| `published_at` | オッズの公式発表日時。現在以前かつ対象発走前の観測を選び、発表からの経過時間を計算する |
| `announced_at` | WF、AV/JC、馬体重read modelの発表日時。欠測は不明のまま保持する |
| `training_date` + `training_time` | 調教の実施日時。同日分は時刻を確認できる場合だけ使い、日付から朝の実施と推測しない |
| 外部観察の `observed_at` | 出典付きで明示された観察日時。同日分はタイムゾーンも必要 |
| `analysis_at` / 現在日時 | サーバーが実行時に取得した分析時刻。データの取得・発表時刻へ転用しない |
| `history_before_at` / `history_before_date` | 対象レースと現在から決まる検索範囲。観測時刻やDBの収録完了時刻を表さない |
| `created_date` | 原票の作成日。日内の順序・取得時刻・当時の利用可能性を推測する根拠にしない |
| `source_sequence` / `artifact_hash` | 原票の順序・同一性や決定的な並び順のための識別子。日時へ変換しない |

* `odds_table` は対象レースと現在時刻から発走前の発表観測を自動選択します。モード指定はありません。ステージ1/2だけを使い、最終・確定値では補完しません。
* 実際のDB取得時刻は得られません。取得時刻・取得からの経過時間・取り込み遅延の出力項目は設けず、発表日時・分析日時から推測もしません。
* 結果の公開時刻も取得していません。当日の既往成績は既知の発走予定時刻と収録済みの完全な結果状態で判定し、過去時点で取得できたことの証明には使いません。
* 複勝・ワイドの時系列集計は「オッズ上下限の中点」を代表値として扱い、確定オッズを発走前オッズとして代用しません。

### 3. 血統・脚質

* **血統指定**: 表示文字列ではなく `relation_code`（`sire`, `dam`, `dam_sire`）および `parent_side`（`paternal`, `maternal`）で特定。
* **脚質マッピング (`running_style_code`)**: `1/逃げ` → `front_runner`、`2/先行` → `stalker`、`3/差し` → `closer`、`4/追込` → `deep_closer`、その他 → `unknown`。

### 4. 調教データ妥当性判定

* 集計対象の妥当域: 5ハロン `45〜120秒` / 4ハロン `35〜100秒`
* 詳細出力ツールは `recent_history` に `time_4f`、`time_6f`、区間時計と出典を返します。
* `session_count`、`comparable_session_count`、`all_history_returned` で有効調教数、自己内比較に使える件数、履歴の省略有無を示します。

### 5. ツールごとの情報範囲

発走前の取得範囲・現在観測・結果の完全性は[予想コンテキスト](forecast-context.md)、
モデルの入力・欠測処理・確率の正規化は[モデル開発](model-development.md)を参照してください。
プロフィールや血統、結果参照、カスタムSQLの日時制限はツールごとに異なります。
[ツールリファレンスの日付基準](tool-reference.md#日付基準の種類)で確認できます。

## 🔒 DB 権限と接続モード

* **トランザクション**: 開始時に `READ ONLY` を明示指定。
* **推奨設定**: MCP サーバーが使用する PostgreSQL ユーザー自体も、DB レベルで参照専用権限（`SELECT`）のみを付与したユーザーを使用してください。

### 結果段階と観測の完全性

`is_final_result=false` は結果が未収録という意味ではありません。中央のステージ6には
`result_status_code=provisional_complete` かつ `is_complete_result=true` の全頭速報があります。
完了実績を集計するライブツールはこの状態を明示して含め、3着・5着までの部分速報を含めません。
固定モデルの履歴は確定・完全な結果に限ります。`result_scope="official"` は結果段階の指定であり、
過去時点の情報を再現する指定ではありません。

現在の出走変更はAV/JC、天候馬場はWF、馬体重は専用read modelの観測として扱います。
発表時刻不明の通知、収録0件、保存済みの最新値だけでは、配信元の最新性や収録完了を保証しません。
具体的な採用条件と出典は[予想コンテキスト](forecast-context.md#現在観測と欠測)にまとめています。
